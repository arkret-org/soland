# Storage backend transition inventory

This inventory covers paired mutating commands in `crates/storage-memory/src`
and `crates/storage-postgres/src`. A command is a transition candidate only
when it contains a business decision over previously durable state. Plain
CRUD, encoding/decoding, pagination, TTL deletion, SQL locking helpers and
projection queries are intentionally excluded: their branch structure is a
persistence concern, not a second business state machine.

The protocol specifications remain authoritative for wire-visible decisions.
Operational leases, SQL row locks and retry bookkeeping are local durability
mechanisms and MUST NOT create protocol state or authorization facts.

## Non-candidates

The paired `accounts`, `audit`, `blobs`, `governance`, `member_identity`,
`notifications`, `policy`, `projection`, `publication_evidence`, `sessions` and
`signal` modules expose CRUD, append-only records or backend-local query/index
maintenance. They have no second command-dependent business state machine to
extract. PostgreSQL-only schema/registry/settings/state-resolution helpers and
Memory-only fault injection are also outside this convergence boundary.

## Oracle policy

- A transition with protocol-visible outcomes uses one async oracle in
  `soland-storage` and both adapters invoke it.
- A pure decision table lives beside its storage port and is called while the
  adapter holds its own mutex, row lock or transaction.
- Adapter-private tests cover SQL constraints, rollback, row locking,
  concurrency and Memory fault injection only; expected business outcomes
  belong to the shared oracle.
- Federation outbox and approval nonce are established shared implementations
  and MUST not be reimplemented by an inventory-driven refactor.
